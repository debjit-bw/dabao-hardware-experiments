# Light client

Before this, the device verified every byte of state against the parent header's state root,
but took the **header itself** from the host. A malicious host could invent a world (a fake
state root) and simulate a drain as a harmless transfer, and it could set the clock the daily
limits run on. The light client removes both: **the device signs only on a parent block that
Ethereum's sync committee signed**, and it checks that itself.

Code: `crates/light-client` (protocol, host-testable), `crates/verifier/src/lc.rs` (state,
persistence), `host/dabao-host/src/lc.rs` (fetching only: every byte it sends is verified).

## How it works

1. **Trust anchor (firmware).** `light_client::anchor`: the SSZ root of the sync committee of
   period 1419, generated by `dabao-host lc-anchor` from the finalized checkpoint at slot
   11630080. The checkpoint root was cross-checked on two independent beacon nodes (Lodestar,
   publicnode), and the bootstrap's `current_sync_committee` branch (gindex 2945) was verified
   against it. Independent confirmation: the real hand-off from period 1418, verified by the
   device's code, lands exactly on this root (test `handoff_1418_to_1419…`).
2. **Committee keys (per boot).** The host uploads the 512 keys (25 KB). The device accepts them
   only if they hash to the root it trusts, then decompresses them once into RAM (6.9 s on the
   chip). The subgroup check is skipped because the root pins keys that a canonical beacon
   state already validated on deposit; with it the load takes 16.2 s.
3. **Hand-offs (every 8192 slots, ~27 h).** An update signed by the current committee (2/3
   participation) carries the next committee and its branch into the signed header's state
   (gindex 2946). The device checks both, then persists the new root and period.
4. **Every transaction.** `SimInput.lc` is a `HeaderProof`: a beacon header signed by the
   current committee, plus `execution_branch`, proving `execution_block_hash` into the header's
   body (gindex 2856, Gloas). The device requires:
   - the signature verifies (2/3 of 512);
   - the branch verifies;
   - `keccak(parent_header) == execution_block_hash`;
   - the simulated block is the parent's number + 1 and its timestamp + 12 s (**trusted
     time** for the policy);
   - the attested slot is not older than the highest slot already used for a signature (a
     **ratchet**, persisted).

   Without a valid proof nothing is signed (simulation still runs, marked
   `HEADER NOT VERIFIED`).

RRAM: app slots 208–209 (claimed), holding the committee root and
`"DLC1" ‖ period ‖ highest slot`.

The host takes the parent block from the latest *optimistic update* (the newest head the
committee signed, seconds old) and builds the witness at that block.

Host tests (real data): the anchor committee loads and others or a modified one don't; the
1418→1419 hand-off verifies, and a forged next committee or the wrong signing committee fails;
a header proof verifies and a different execution hash fails; a tampered header, a claimed
extra participant and < 2/3 participation all fail.

## Assumptions and limits

- **Honest sync-committee supermajority** (the standard light-client assumption): 2/3 of 512
  randomly sampled validators don't sign a non-canonical header. Unlike attestations, sync
  committee signatures aren't slashable today.
- **"Latest" is relative.** The device has no clock, so it knows a header is real and not older
  than one it already used, not that it is the newest. The ratchet only advances when
  something is signed. Within that window, a stale state shows up as an invalid nonce or, for
  anything else, is the same gap as simulation-to-inclusion (planned: an on-chain
  postcondition in the Safe flow).
- Hand-offs are accepted with 2/3 participation on any signed header in the period. The spec
  also tracks finality for this; we rely on the supermajority alone.
- Gindices are Gloas's (measured on real proofs); headers before the Gloas fork are refused. A
  future fork that moves these fields needs a firmware update (as with the fork schedule).
- After months offline the anchor goes past the weak-subjectivity period and needs a fresh
  firmware anchor, as for any proof-of-stake light client.
- Beacon data comes from a node with the light-client server enabled (Lodestar's public Sepolia
  node; publicnode's beacon API has none). The node is untrusted: it can only withhold data.
